# 모델 비교: 대본 단위 판단

판정기는 대본 하나를 모델에 한 번 보내고 여섯 가지 판단을 JSON으로 받는다(README 3.4절). 이 문서는 그 판단을 맡길 모델을 고른 과정과 결과다.

- 환경: Apple M5 Pro, 메모리 48GB, Ollama 0.31.1, 판정기 0.4.0
- 원자료: `docs/model-comparison-raw.txt` (본 비교), `docs/model-comparison-trials-raw.txt` (판정기에 넣기 전의 시험)
- 다시 실행: `npm run compare-models -- gemma4:e4b qwen3.5:4b qwen3.5:2b gpt-oss:20b=low`

## 1. 후보


| 모델            | 파라미터  | 양자화      | 디스크   | 라이선스       |
| ------------- | ----- | -------- | ----- | ---------- |
| `gemma4:e4b`  | 7.5B  | Q4\_K\_M | 6.6GB | Apache-2.0 |
| `gpt-oss:20b` | 20.9B | MXFP4    | 13GB  | Apache-2.0 |
| `qwen3.5:4b`  | 4.2B  | Q4\_K\_M | 3.3GB | Apache-2.0 |
| `qwen3.5:2b`  | 1.9B  | Q8\_0    | 2.7GB | Apache-2.0 |


파라미터와 양자화는 `ollama show`, 디스크는 `ollama list`, 라이선스는 `ollama show --license`의 값이다. `exaone3.5:2.4b`도 내려받았지만 이 기기의 Ollama 설정(KV 캐시 q8_0)과 맞지 않아 실행되지 않았다.

## 2. 판정기에 넣기 전의 시험

예시 대본 10개(01~~10)로 임시 스크립트를 돌렸다. 질문 문구는 지금 판정기와 같지만, 시험 1~~3은 단계를 번호로 답하게 했다.


| 시험  | 모델            | 조건            | 결과                                                    |
| --- | ------------- | ------------- | ----------------------------------------------------- |
| 1   | `qwen3.5:4b`  | 생각 끔, 단계 번호   | 10개 모두 형식이 틀렸다. 8개는 JSON 문법부터 틀렸고, 2개는 객체 대신 배열로 답했다  |
| 2   | `gemma4:e4b`  | 생각 끔, 단계 번호   | 형식은 지켰다. 10개 중 6개에서 단계 번호 대신 문장 번호(0, 1, 2, ...)를 적었다 |
| 3   | `gpt-oss:20b` | 생각 low, 단계 번호 | 형식을 지켰고 단계도 대체로 맞았다. 대본당 약 11초                        |
| 4   | `gemma4:e4b`  | 생각 끔, 단계 이름   | 형식을 지켰다. 라벨과 다른 단계는 78문장 중 4개였다. 대본당 약 1.5초           |
| 5   | `qwen3.5:4b`  | 생각 끔, 단계 이름   | 10개 모두 형식이 틀렸다. 답을 배열로 감쌌다                            |
| 6   | `qwen3.5:4b`  | 생각 켬, 단계 이름   | 첫 대본에서 8분이 넘도록 답이 없어 멈췄다                              |


시험 2와 4의 차이 때문에 판정기는 단계를 이름 목록(JSON 스키마의 enum)에서 고르게 한다.

## 3. 본 비교

판정기의 요청(`src/model/review.ts`)을 그대로 써서 대본 12개(90문장)를 모델마다 두 번씩 보냈다. 첫 요청은 모델을 메모리에 올리는 시간이 들어가므로 시간을 재기 전에 한 번 따로 보냈다.


| 모델                     | 첫 답의 형식 오류  | 라벨과 다른 단계 | 두 번 보낸 답이 다른 대본 | 대본당 시간 | 입력 / 출력 토큰 (12개 합) |
| ---------------------- | ----------- | --------- | --------------- | ------ | ------------------ |
| `gemma4:e4b`           | 0 / 12      | 4 / 90    | 0 / 12          | 1.20초  | 7,824 / 1,293      |
| `gpt-oss:20b` (생각 low) | 0 / 12      | 12 / 90   | **7 / 12**      | 9.40초  | 14,452 / 695       |
| `qwen3.5:4b`           | **12 / 12** | -         | 0 / 12          | 1.24초  | 7,355 / 660        |
| `qwen3.5:2b`           | **12 / 12** | -         | 0 / 12          | 0.93초  | 7,355 / 787        |


- 시간과 토큰은 Ollama가 응답과 함께 돌려준 값이다. 첫 번째 보낸 답만 더했다.
- `gpt-oss:20b`의 출력 토큰에 생각 단계의 토큰이 들어가는지는 확인하지 못했다.
- `qwen3.5:4b`는 답을 배열로 감쌌고, `qwen3.5:2b`는 단계 배열의 길이가 문장 수와 달랐다.

### 대조 대본과 기대값에 대한 반응

형식을 지킨 두 모델만 비교한다.


| 확인                                  | 기대    | `gemma4:e4b`  | `gpt-oss:20b`            |
| ----------------------------------- | ----- | ------------- | ------------------------ |
| 11번, 인사뿐인 훅의 내용                     | false | false         | false                    |
| 12번, 본문이 답하지 않는 훅의 해소               | false | **true (놓침)** | false                    |
| 06번, 목록형의 다음 항목(문장 3, 5)을 화제 끊김으로 봄 | 안 봄   | 안 봄           | **봄 (문장 3, 5)**          |
| 05번, 젠투펭귄 문장(문장 6)을 화제 끊김으로 봄       | 봄     | 봄             | 봄                        |
| 0번 문장(훅)을 훅이 아닌 단계로 봄               | 안 봄   | 0개            | 5개 (03, 06, 08, 09, 11번) |


`gpt-oss:20b`의 값은 첫 번째 답 기준이다. 두 번째 답은 7개 대본에서 달랐다.

## 4. 결론

기본 모델을 `gemma4:e4b`로 정했다.

- 형식 오류가 없었고, 같은 대본에 두 번 모두 같은 답을 냈다. 판정 결과를 기록으로 쌓아 비교하는 판정기에서 재현성은 필수다.
- 대본당 1.2초로 `gpt-oss:20b`보다 약 8배 빠르고 디스크는 절반이다.
- 라벨과 다르다고 본 문장이 4개로 가장 적었다.

`gemma4:e4b`의 약점은 훅의 해소다. 12번 대조 대본을 놓쳤고, 12개 대본 모두에 true를 주었다. `gpt-oss:20b`는 이 대본을 잡았지만 같은 대본에 다른 답을 냈다. 이 항목은 지시 문구를 다시 쓰고 대조 대본을 늘려서 다시 확인해야 한다(README 4.6절).

## 5. 한계

- 대본 12개, 라벨과 기대값 모두 Claude가 만들었다. "라벨과 다른 단계"는 정확도가 아니다.
- 질문 문구는 시험 2와 4를 거쳐 `gemma4:e4b`에 맞춰 고쳤다. 같은 대본으로 고치고 다시 쟀으므로 `gemma4:e4b`에 유리할 수 있다.
- 시간은 한 번 잰 값이다.
- `gpt-oss:20b`의 답이 왜 실행마다 다른지는 확인하지 못했다. 생각 단계를 끌 수 없는 모델이라 그 영향일 수 있다는 것은 추정이다.
