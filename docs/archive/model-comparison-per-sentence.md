# 작은 모델 비교 기록 (문장 단위 질문, 폐기한 방식)

> 이 문서는 판정기가 문장마다 예, 아니오 질문을 보내던 때(판정기 0.3.0)의 기록이다.
> 이 방식은 예시 대본 10개에 모델을 177번 부르고, 라벨이 맞는 문장을 많이 짚어서 폐기했다.
> 지금 판정기는 대본 하나에 모델을 한 번 부른다. 그 비교는 `docs/model-comparison.md`에 있다.
> 이 실험에 쓴 문항(`eval/model-cases.ts`)과 이전 비교 스크립트는 저장소에서 지웠다.
> 결정을 바꾼 과정을 남기려고 이 문서를 보관한다.

- 원자료: `docs/archive/model-comparison-per-sentence-raw.txt`
- 이 방식으로 예시 대본 10개를 판정한 기록: `docs/archive/sample-scripts-per-sentence-v0.3.0.jsonl`

## 1. 목적

판정기의 일부 항목은 문장의 뜻을 봐야 한다. 이 항목들은 로컬에서 도는 작은 오픈 모델에 예, 아니오 질문을 해서 잰다. 이 실험은 어느 모델을 기본 모델로 쓸지 정하려고 했다.

조건은 세 가지다.

- 프론티어 모델을 쓰지 않는다. 가중치가 공개된 모델을 로컬 Ollama로 돌린다.
- 모델 사용량을 줄인다. 그래서 작고 빠른 모델을 우선한다.
- 같은 대본에 같은 결과가 나와야 한다. 판정 결과를 기록으로 쌓아 시기별로 비교하기 때문이다.

## 2. 환경

| 항목      | 값                                               |
| --------- | ------------------------------------------------ |
| 기기      | Apple M5 Pro, 메모리 48GB                        |
| 실행기    | Ollama 0.31.1                                    |
| 호출 방식 | `POST /api/chat`, 스트리밍 없음                  |
| 무작위성  | `temperature: 0`, `seed: 0`                      |
| 답의 형태 | `format`에 JSON 스키마 `{"answer": "yes"\|"no"}` |
| 생각 단계 | `think: false`. `gpt-oss:20b`만 `think: "low"`   |

시스템 프롬프트는 아래 한 줄이다.

```
너는 쇼츠 영상 대본을 검사하는 분류기다. 질문을 읽고 yes 또는 no 중 하나로만 답한다.
```

### 비교하지 못한 모델

- `exaone3.5:2.4b`: 내려받았지만 실행되지 않았다. 오류는 `K cache type q8_0 with block size 32 does not divide n_embd_head_k=80`이다. 오류 내용으로 보면 이 기기의 Ollama 서버는 KV 캐시 형식이 q8_0으로 설정돼 있고, 이 모델의 구조와 맞지 않는다. 서버 설정은 바꾸지 않았고 모델은 지웠다. 라이선스는 확인하지 않았다.
- `hyperclovax-seed`, `kanana`, `midm`: Ollama 공식 저장소에서 이 이름으로 찾지 못했다. 개인이 올린 모델은 확인하지 않았다.

### 내려받는 양을 줄이려고 뺀 모델

## 4. 방법

### 문항

문항은 `eval/model-cases.ts`에 있는 54개다. 판정기가 실제로 쓰는 질문 여섯 종류로 만들었다. 질문 문구는 `src/model/questions.ts`의 함수가 만든다.

| 질문 종류     | 문항 수 | 묻는 것                                             | 쓰는 판정 항목   |
| ------------- | ------- | --------------------------------------------------- | ---------------- |
| 타입 일치     | 14      | 문장이 타입 라벨의 역할을 하는가                    | 타입 일치        |
| 문장 간 연결  | 8       | 뒤 문장이 앞 문장과 같은 화제를 이어 가는가         | 문장 간 연결     |
| 가리키는 대상 | 8       | 지시어가 무엇을 가리키는지 앞 문장에서 알 수 있는가 | 가리키는 대상    |
| 훅의 질문     | 8       | 첫 문장에 영상이 다룰 구체적인 내용이 있는가        | 훅의 질문        |
| 훅의 해소     | 8       | 뒤의 문장들이 첫 문장의 질문이나 주장에 답하는가    | 훅의 해소        |
| 영향          | 8       | 문장이 시청자에게 생기는 이득이나 손해를 말하는가   | 문장별 흥미 장치 |

타입 일치를 뺀 다섯 종류는 정답이 예인 문항과 아니오인 문항이 4개씩이다. 타입 일치는 예가 8개, 아니오가 6개다.

### 절차

1. 모델을 메모리에 올리려고 첫 문항을 한 번 묻고 결과를 버린다.
2. 54개 문항을 차례로 묻는다. 이때 걸린 시간을 문항 수로 나눠 문항당 시간을 구한다.
3. 각 문항을 한 번 더 물어서 답이 같은지 본다.

실행 명령은 아래와 같다.

```
node scripts/compare-models.ts qwen3.5:4b qwen3.5:2b gemma4:e4b gpt-oss:20b=low
```

## 7. 실행하면서 확인한 것

- **답의 형태**: `qwen3.5:4b`는 `think: false`로 부르면 `format`의 JSON 스키마를 지키지 않고 `yes`만 답했다. `think`를 빼고 부르면 `{"answer": "yes"}`로 답하지만 생각 단계가 돈다. 판정기는 두 형태를 모두 읽도록 고쳤다. 첫 실행에서는 이 문제 때문에 `qwen3.5:4b`의 54개 문항이 모두 응답 실패로 집계됐다. 그 결과는 모델의 성능이 아니어서 위 표에 넣지 않았다.
- **재현성**: 네 모델 모두 같은 문항을 두 번 물었을 때 답이 같았다. 확인한 조건은 같은 기기, 같은 서버, 연이은 두 번의 호출이다. 다른 기기나 다른 Ollama 버전에서의 재현성은 확인하지 않았다.
- **생각 단계**: `gpt-oss:20b`는 생각 단계를 끌 수 없어서 `low`로 돌렸다. 문항당 시간이 다른 모델보다 긴 이유에 이 단계가 들어 있다.

## 8. 결론

기본 모델을 `qwen3.5:4b`로 정했다.

- 정답 수가 가장 큰 모델(`gpt-oss:20b`)과 한 문항 차이다.
- 문항당 시간이 `gpt-oss:20b`의 약 6분의 1이고 크기가 약 4분의 1이다.
- `qwen3.5:2b`는 질문 두 종류에서 정답률이 절반 수준이라 쓰기 어렵다.

예시 대본(문장 6개)을 판정기로 끝까지 실행했을 때 모델을 13번 불렀고, 형태소 분석기와 모델을 불러오는 시간을 포함해 8초가 걸렸다.

## 9. 한계

- **문항을 내가 지어냈다.** 문장과 정답 모두 실험한 쪽이 만들었다. 실제 쇼더스 대본의 문장이 아니다.
- **정답이 분명한 문항만 넣었다.** 실제 대본에는 경계가 모호한 문장이 있다. 실제 정확도는 이 점수보다 낮을 수 있다.
- **문항 수가 적다.** 질문 종류마다 8~14개다. 한 문항이 종류별 정답률을 7~13%포인트 움직인다. 53개와 52개의 차이는 의미 있는 차이라고 볼 수 없다.
- **문구를 같은 문항으로 고쳤다.** 틀린 문항을 보고 문구를 고친 뒤 같은 문항으로 다시 쟀다. 고친 뒤의 점수는 새 문항에서의 점수보다 높게 나온다.
- **한 번만 쟀다.** 시간은 모델마다 한 차례 실행한 값이다. 다른 프로그램의 영향을 받았을 수 있다.
- **사람의 판단과 비교하지 않았다.** 정답을 정한 사람이 한 명이다. 여러 사람이 같은 답을 내는지 확인하지 않았다.

보고서에 쓰려면 실제 대본에서 뽑은 문장으로 문항을 새로 만들고, 문구를 고칠 때 쓰는 문항과 점수를 재는 문항을 나눠야 한다.

## 10. 다시 실행하는 방법

```
ollama pull qwen3.5:4b

```

모델 이름 뒤에 `=low`를 붙이면 생각 단계를 그 수준으로 켠다. 문항을 바꾸려면 `eval/model-cases.ts`를 고친다.

## 부록. 고쳐 쓰기 예비 실험

판정기가 문장을 고쳐 쓰는 기능을 검토하려고 같은 날 한 실험이다. 검토한 뒤 이 기능은 넣지 않기로 정했다. 판정기는 대본을 고치지 않고 그대로 넘긴다. 이 부록은 그 결정의 근거로 남긴다. 문항 여섯 개를 모델마다 한 번씩 물은 것이어서 비교라기보다 살펴본 수준이다. 실험에 쓴 코드는 저장소에 넣지 않았다.

설정은 위 비교와 같고, 답의 형태만 제한하지 않았다. 시스템 프롬프트는 아래와 같다.

```
너는 쇼츠 영상 대본의 문장을 고치는 편집자다. 고친 문장 하나만 출력한다. 설명을 붙이지 않는다. 원래 문장에 없는 사실, 숫자, 이름을 더하지 않는다.
```

### 관찰한 것

- **말투가 바뀐다.** 원래 문장은 "-습니다"로 끝난다. 답 가운데 "-이다", "-없다", "-져요", "-있어요"로 끝난 것이 있다.
- **뜻이 바뀐다.** `qwen3.5:4b`는 "3분"을 "세 분"으로 바꿨다. `gemma4:e4b`는 "대책은 아직 없습니다"를 "대책은 미흡합니다"로 바꿨다. `gpt-oss:20b`는 훅에서 "더 냅니다"를 "될 수 있어요"로 바꿨다.
- **내용이 빠진다.** `qwen3.5:4b`는 긴 문장에서 요금과 물가를 뺐다.
- **문장 간 연결은 세 모델 모두 어려워했다.** 앞 문장의 내용을 뒤 문장에 다시 넣거나, 없던 인과 관계를 만들었다. `gemma4:e4b`는 서술문을 행동을 요청하는 문장으로 바꿨다.
- **지시어를 대상의 이름으로 바꾸는 일은 세 모델 모두 해냈다.**
- **예, 아니오 질문에서 고른 `qwen3.5:4b`는 고쳐 쓰기에서 여섯 문항 중 한 문항만 쓸 만한 답을 냈다.** 판정에 맞는 모델과 고쳐 쓰기에 맞는 모델이 다를 수 있다.
